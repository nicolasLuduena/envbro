# Issue 4: CI/CD Reliability (HTTP Gateway)

## Context
Use Case: A GitHub Action or Jenkins pipeline needs to inject environment variables to build the app or run integration tests.

**The Problem**:
1.  **Latency**: CI runners are ephemeral. Waiting 5-30 seconds for P2P Discovery (DHT) to find peers and sync headers is unacceptable for a fast build pipeline.
2.  **Firewalls**: Corporate CI often blocks UDP/P2P traffic, allowing only HTTP/HTTPS.
3.  **Reliability**: P2P is eventually consistent. CI needs strong consistency/availability.

**The Solution**:
A dedicated "Gateway Mode" that acts as a bridge between the P2P swarm and the HTTP-speaking CI runner.

## Component: `envbro-gateway`
A lightweight HTTP server that runs permanently (e.g., on a VPS, internal Kubernetes cluster, or even a Raspberry Pi in the office) and keeps the P2P vault synced.

### API Specification
- **Endpoint**: `GET /api/v1/secrets?env=production&project=my-app`
- **Auth**: Bearer Token (A static "Service Account Token" generated by the admin, unrelated to the P2P keys).
- **Response**: JSON object `{ "API_KEY": "..." }`.

## Architecture
1.  **The Bridge**: The Gateway process holds the `Read Key` for the project and stays connected to the swarm. It always has the latest version on disk.
2.  **The Consumer**: The CI script runs:
    ```bash
    curl -H "Authorization: Bearer $ENVBRO_TOKEN" https://my-gateway.internal/secrets | envbro inject
    ```
    (Or simply parses the JSON).
